# WebMCP editor adapter

This integrates the editor portion of PR #7 onto current develop. All additions and fixes live in project `plugin/` code. No `three.js/` source is changed. Existing Unity rotation conversion, outliner behavior and normalized meta signal registry are preserved.

The host exposes the browser's WebMCP tools. This iframe exposes exact `webmcp-*` REQUEST actions through the existing INIT/REQUEST/RESPONSE bridge. `webmcp-get-capabilities` lists the supported actions. Every WebMCP response correlates the original request ID. INIT config supplies `hostSessionId`, `id` and `saveable`; once a host session is supplied, WebMCP requests must carry that session ID. The bridge pins the parent origin, and reinitialization/destroy invalidates pending work and replies.

`webmcp-get-entity-state` returns the current `{meta, events}`, `entityId`, `entityVersion`, `changed`, `loading`, `source: "live-editor"` and `contextGeneration`. It serializes live editor state, including unsaved edits. `webmcp-mark-entity-saved` accepts `expectedEntityVersion` after backend acknowledgement and only clears the saved snapshot if that version still matches. Scene read and acknowledgement use `webmcp-get-scene-state` and `webmcp-mark-scene-saved` with `expectedSceneVersion`.

Placement requests accept `operationId` (the host draft ID). The editor reserves the ID before loading; repeated attempts in the same session are rejected. Entity placement also accepts `expectedEntityVersion`; scene placement requires `expectedSceneVersion`. Both serialize concurrent placements, validate the editing context after loading, and reject edits or permission/session changes during the wait. Pending waits stop on navigation and time out after 60 seconds. Underlying third-party loaders are not modified; a cancelled loader may finish fetching, but cannot insert into the editor. Missing assets fail instead of inserting silent placeholders. Resources and normalized signals become shared only after insertion succeeds. If insertion succeeds but serialization fails afterward, the response remains acknowledged with `readBackVerified: false`.

Batch commands use the project-owned `WebMcpBatchCommand` policy, including rollback of a partially executed child. A failed rollback is explicitly reported; the adapter does not claim the state was restored in that case. Clone operations build a complete object/component ID map before rewriting internal references; external references remain unchanged. Destructive node previews include components and commands in their conflict fingerprint.

## Compatibility and validation

`AtomicCommands.ts` adapts the current upstream `History` behavior, which queues a command before executing it. The adapter snapshots `undos`, `redos`, `idCounter` and `lastCmdTime` to restore history bookkeeping when command execution fails. This is an explicit coupling to the pinned editor version, protected by tests using the real upstream History/Command classes. Compound commands retain upstream serialization; persisted history rehydration remains governed by the editor and is not a durable cross-session transaction log. Operation IDs are session-local, not backend idempotency keys.

Run `npm run typecheck` and `npm run test:webmcp` (Node 22.15+ with `node:module.registerHooks`, exercised on Node 24). The suite covers real Three.js nodes, batch undo/redo and rollback, stale deletion, clone references, live serialization, save acknowledgement, concurrent placement, session cancellation, insertion failure and registry consistency, request correlation and origin filtering. No claim is made that arbitrary asset/network failures can be cancelled inside vendor code or that browser-native WebMCP is supported in every browser.
